# قاعدة PostgreSQL المركزية — نظام دفتر الدكان

## الحالة

هذه الحزمة هي **مرشح إنتاج PostgreSQL v1.0.0** المبني مباشرة على مخطط SQLite المحلي v1.1، مع إضافات الخادم الضرورية للمستخدمين والاشتراكات والتراخيص والمزامنة والاستعادة والتدقيق المركزي.

تم تنفيذ مراجعة ثابتة آلية شملت:

- 60 جدولًا إجمالًا.
- 43 جدولًا مشتركًا منطقيًا مع SQLite.
- 17 جدولًا مركزيًا للخادم.
- 146 مفتاحًا خارجيًا.
- 55 فهرسًا.
- 11 View.
- 50 Trigger وتعريف Trigger ديناميكي.
- 30 Function.
- 756 فحصًا ثابتًا ناجحًا دون فشل.

ملف `06_runtime_tests.sql` يحتوي اختبارات تشغيل وتكامل فعلية، لكنه يجب أن يُشغّل على خادم PostgreSQL حقيقي. بيئة إنشاء هذه الحزمة لم تحتوِ على خادم PostgreSQL قابل للتشغيل، لذلك لا يُدّعى أن اختبارات التشغيل نُفذت هنا.

## البنية

### `ledger`

بيانات الدكان المالية والتشغيلية القابلة للمزامنة مع SQLite، مثل:

- العملاء والموردون.
- المنتجات والوحدات.
- المبيعات والمشتريات.
- الدفع المختلط: كاش، بنك، محفظة، وحسابات تحويل متعددة.
- ديون العملاء والتزامات الموردين.
- حركات الأموال والمخزون.
- المصاريف وحساب المالك.
- المرتجعات والتصحيحات والفترات المحاسبية.

### `platform`

بيانات الخادم فقط:

- المستخدمون وتسجيل الدخول.
- عضوية الدكاكين والصلاحيات.
- الجلسات وRefresh Tokens.
- خطط الاشتراك والاشتراكات.
- إصدار التراخيص الموقعة للأجهزة.
- النسخ الاحتياطية والإجراءات الإدارية.

### `sync`

طبقة المزامنة:

- منع تكرار `operation_id`.
- Change Feed متسلسل باستخدام Cursor.
- حالة مزامنة كل جهاز.
- التعارضات والعمليات الفاشلة.
- Snapshots لاستعادة هاتف جديد.

### `audit`

سجل تدقيق مركزي غير قابل للتعديل.

## سياق الدكان داخل NestJS

كل Request مالي أو مزامنة يجب أن يعمل داخل Transaction واحدة. في بداية المعاملة اضبط:

```sql
SELECT set_config('app.store_id',   :store_id, true);
SELECT set_config('app.user_id',    :user_id, true);
SELECT set_config('app.device_id',  :device_id, true);
SELECT set_config('app.request_id', :request_id, true);
```

القيمة `true` تجعل الإعداد محصورًا داخل المعاملة. سيستخدم RLS هذه القيم لمنع قراءة أو كتابة بيانات دكان آخر.

## قواعد إلزامية للـBackend

- لا يتصل Flutter مباشرة بـPostgreSQL.
- جميع العمليات تمر عبر NestJS وDrizzle.
- لا تحفظ أجزاء البيع أو الدفع في معاملات منفصلة.
- اطلب `sync.claim_operation` في بداية عملية Push لمنع التكرار.
- عند فشل أي خطوة نفّذ Rollback كاملًا.
- لا تعدّل دفاتر الحركات أو تحذفها؛ أنشئ حركة عكسية.
- لا تستخدم `float` أو `double` للأموال أو الكميات.
- الأموال في `bigint` بأصغر وحدة نقدية.
- الكميات في `bigint` بأجزاء الألف.
- الوقت في PostgreSQL من نوع `timestamptz`، بينما عقد المزامنة يمكن أن ينقل Epoch milliseconds.

## المخزون والتزامن

`inventory_movements` هو المصدر الحقيقي، و`stock_balances` Cache محمي. Trigger المخزون:

- يقفل رصيد المنتج باستخدام `FOR UPDATE`.
- يرفض Snapshot قديمًا برمز تعارض.
- يمنع المخزون السالب حسب إعداد الدكان أو المنتج.
- يحدّث Cache داخل المعاملة نفسها.

## الدفع المختلط

الفاتورة الواحدة يمكن أن تحتوي عدة أسطر داخل `sale_payments`، وكل سطر يرتبط بحساب مالي مختلف وحركة في `money_movements`.

مثال:

- 40 شيكل كاش.
- 35 شيكل بنك.
- 25 شيكل محفظة.

كل حساب يرتفع بقيمته فقط. الجزء الآجل لا يدخل أي حساب مالي؛ يسجل في `customer_ledger_entries` كذمة على العميل.

## Drizzle

ملفات SQL هي مصدر الحقيقة للقيود المتقدمة وRLS وTriggers. بعد تطبيقها يمكن سحب المخطط إلى Drizzle أو كتابة تعريفات TypeScript المطابقة. لا تحذف الدوال والسياسات عند إنشاء Migrations جديدة.

يوجد ملف إعداد أولي:

- `drizzle.config.ts.example`

## توافق SQLite

أضيفت متطلبات اليوم التشغيلي التي كانت ناقصة من SQLite v1.1:

- المنطقة الزمنية.
- بداية اليوم التشغيلي.
- نهاية اليوم التشغيلي.
- نمط 24 ساعة أو وقت مخصص.

يجب تسليم مطور الموبايل أيضًا:

- `sqlite_v1_2_settings_patch.sql`

وبعد تطبيقه يصبح `PRAGMA user_version = 10200`.
