# دليل دمج مخطط SQLite المحلي — نظام دفتر الدكان v1.1

## 1. حالة المخطط

هذا المخطط هو قاعدة البيانات المحلية المعتمدة للبدء في تنفيذ تطبيق الموبايل بنمط Offline-first. تم إنشاؤه واختباره فعليًا باستخدام SQLite، ويحتوي على:

- 49 جدولًا.
- 8 Views للأرصدة والتقدم المحاسبي.
- 148 Trigger وقيدًا وقائيًا.
- 26 فهرسًا مخصصًا، إضافة إلى الفهارس التلقائية.
- `user_version = 10100` للدلالة على الإصدار 1.1.0.

نتائج الفحص النهائية:

- `PRAGMA quick_check = ok`
- `PRAGMA integrity_check = ok`
- `PRAGMA foreign_key_check` بلا أخطاء.
- نجاح 25 من 25 اختبارًا وظيفيًا وماليًا حرجًا.

## 2. الحد الأدنى للبيئة

يجب استخدام نسخة حديثة من SQLite تدعم:

- STRICT tables.
- JSON functions، ومنها `json_valid`.
- Partial indexes.
- Upsert باستخدام `ON CONFLICT ... DO UPDATE`.

الحد العملي المقترح هو SQLite 3.38 أو أحدث.

## 3. إعداد الاتصال الإلزامي

يجب تطبيق الإعدادات التالية عند فتح كل اتصال بقاعدة البيانات:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
PRAGMA recursive_triggers = ON;
```

لا يجوز الاعتماد على أن إعداد `foreign_keys` سيبقى مفعلًا تلقائيًا بين الاتصالات.

## 4. قواعد البيانات المشتركة مع PostgreSQL

| المفهوم | SQLite المحلية | PostgreSQL المركزية |
|---|---|---|
| المعرّف | `TEXT` يحوي UUID | `uuid` |
| المبلغ | `INTEGER` باسم ينتهي بـ `_minor` | `bigint` |
| الكمية | `INTEGER` باسم ينتهي بـ `_milli` | `bigint` |
| التاريخ | Unix milliseconds UTC في `INTEGER` | `timestamptz` أو `bigint` في عقد المزامنة |
| القيم المنطقية | `INTEGER` بقيمتي 0 و1 | `boolean` |
| JSON | `TEXT` مع `json_valid` | `jsonb` |
| الإصدار | `version INTEGER` | `version bigint/integer` |

المبالغ لا تخزن باستخدام `REAL` أو `double` أو `float`.

## 5. قاعدة المعاملة الذرية

كل عملية مركبة يجب تنفيذها داخل Transaction واحدة. لا يجوز حفظ أجزاء العملية ثم اعتمادها لاحقًا في Transaction مختلفة.

مثال عملية البيع:

1. إنشاء `sales` بحالة `draft`.
2. إنشاء `inventory_movements` اللازمة.
3. إنشاء `sale_items` وربطها بحركات المخزون.
4. إنشاء `money_movements` للدفعات.
5. إنشاء `sale_payments`.
6. إنشاء `customer_ledger_entries` للدين عند الحاجة.
7. تحديث البيع إلى `posted`.
8. إضافة سجل `sync_outbox`.
9. تنفيذ `COMMIT`.

عند فشل أي خطوة يجب تنفيذ `ROLLBACK` للعملية كاملة. Views الدفاتر تعتمد على الحركات، لذلك لا يجوز Commit لعملية بقيت في حالة Draft ومعها حركات دفترية نهائية.

## 6. المصادر المحاسبية للحقيقة

- المخزون: `inventory_movements` هو المصدر الحقيقي.
- `stock_balances` جدول Cache يحدّث تلقائيًا، ولا يعدل مباشرة.
- رصيد الحسابات: `money_movements`.
- دين ورصيد العميل: `customer_ledger_entries`.
- التزام ورصيد المورد: `supplier_ledger_entries`.
- موقف المالك: `owner_ledger_entries`.
- الإجماليات المحفوظة داخل الفواتير تستخدم للسرعة والتحقق، لكن يجب بناؤها من البنود.

## 7. قواعد لا يجوز تجاوزها في التطبيق

- عدم تنفيذ DELETE للمعاملات المالية أو المخزنية المعتمدة.
- استخدام الأرشفة للعميل والمورد والمنتج والحساب.
- استخدام حركة عكسية عند التصحيح أو الإلغاء.
- عدم تعديل `stock_balances` مباشرة.
- عدم إنشاء دين لبيع مجهول العميل.
- عدم توزيع دفعة فوق الرصيد المتبقي للفاتورة.
- عدم إغلاق فاتورة شراء قبل اكتمال الاستلام.
- عدم إدخال عملية في فترة مغلقة.
- عدم تجاوز حد الدين عندما تكون السياسة `block`.
- عدم السماح بالمخزون السالب إلا عندما تسمح إعدادات الدكان أو المنتج بذلك.
- استخدام `operation_id` فريد لكل عملية قابلة للمزامنة.

## 8. التطبيع والبحث العربي

على طبقة التطبيق إنشاء القيم المطَبّعة قبل الحفظ:

- `normalized_name`: إزالة التشكيل وتوحيد صور الألف والمسافات وفق سياسة ثابتة.
- `normalized_phone`: أرقام فقط مع سياسة موحدة للمقدمة الدولية/المحلية.

يجب استخدام السياسة نفسها في الهاتف والخادم لمنع اختلاف نتائج البحث ومنع التكرار.

## 9. المزامنة

- ينشئ الهاتف UUID قبل الاتصال بالخادم.
- تحفظ العملية وسجل `sync_outbox` في Transaction واحدة.
- يرسل NestJS العملية باستخدام `operation_id`.
- PostgreSQL تفرض قيدًا فريدًا على `(store_id, operation_id)`.
- عند نجاح الخادم تتحول حالة Outbox إلى `synced`.
- عند الاستعادة على هاتف جديد يستخدم Bootstrap ثم Pull باستخدام Cursor.
- `sync_inbox_receipts` تمنع تطبيق الحدث المركزي نفسه مرتين.

## 10. النسخ الاحتياطي

لا تنسخ ملف SQLite مباشرة أثناء عمليات كتابة نشطة. استخدم آلية Backup معتمدة أو نفذ Checkpoint مناسبًا، ثم تحقق من:

```sql
PRAGMA quick_check;
PRAGMA foreign_key_check;
```

يجب تشفير النسخة قبل رفعها، وحفظ checksum وإصدار Schema في `backup_metadata`.

## 12. حدود الضمان

المخطط يمنع عددًا كبيرًا من الأخطاء على مستوى قاعدة البيانات، لكنه لا يلغي مسؤولية طبقة التطبيق. سلامة النظام النهائية تتطلب:

- استخدام Transactions كما هو موضح.
- تطبيق تسلسل العمليات الصحيح.
- اختبارات تكامل بين الهاتف وNestJS.
- اختبار Migrations عند كل تحديث.
- مراجعة أمنية وتشفير التخزين المحلي.
- عدم استخدام DB Browser لتعديل قاعدة المستخدم الإنتاجية.
