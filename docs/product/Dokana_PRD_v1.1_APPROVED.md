# **1. الملخص التنفيذي**

نظام دفتر الدكان هو تطبيق موبايل مبسط يحل محل الدفتر الورقي والبرامج
المحاسبية الثقيلة لدى الدكاكين والمحلات الصغيرة. يتيح لصاحب الدكان تسجيل
البيع، متابعة ديون الزبائن، إدارة الموردين، مراقبة المخزون، تسجيل
المصاريف، متابعة الكاش وحسابات التحويل، ومعرفة الربح والسيولة بصورة
مفهومة دون الحاجة إلى خبرة محاسبية.

المنتج يعمل دون إنترنت اعتمادًا على قاعدة SQLite داخل الهاتف، ثم يزامن
البيانات مع Backend مركزي مبني باستخدام NestJS وDrizzle وPostgreSQL عند
توفر الاتصال. يسمح هذا التصميم باستمرار العمل في البيئات ذات الإنترنت
الضعيف، مع توفير النسخ السحابي، الاستعادة على جهاز جديد، إدارة الاشتراك،
وقابلية التوسع مستقبلًا.

النسخة الأولى موجهة لصاحب دكان واحد يستخدم جهازًا رئيسيًا واحدًا. لا تشمل
نظام محاسبة مزدوجًا كاملًا، ضرائب، رواتب، فروعًا متعددة، أو مزامنة متزامنة
بين عدة أجهزة. الهدف هو منتج بسيط في الواجهة، صحيح في قواعده المالية،
وقابل للتدقيق والتوسع.

# **2. المشكلة التي يحلها المنتج**

تعتمد نسبة كبيرة من الدكاكين الصغيرة على دفاتر ورقية أو تطبيقات شديدة
البساطة لتسجيل الديون. هذه الطرق لا تربط الدين بالمبيعات والمخزون
والموردين والحسابات، وتؤدي إلى غموض في الربح والسيولة والالتزامات.

- ضياع أو تلف الدفتر وصعوبة استعادة البيانات.

- عدم معرفة إجمالي دين كل زبون وسجل مشترياته وتسديداته.

- الخلط بين المبيعات، المبالغ المحصلة، والربح الحقيقي.

- عدم معرفة المخزون المتبقي أو تكلفة البضاعة المباعة.

- عدم وجود صورة واضحة عن ديون الموردين والمصاريف المستحقة.

- توزع الأموال بين الكاش وحسابات التحويل دون متابعة موحدة.

- توقف بعض الأنظمة عند انقطاع الإنترنت.

- تعقيد البرامج المحاسبية التقليدية مقارنةً بمهارات المستخدم المستهدف.

# **3. الرؤية والتموضع**

الرؤية: أن يصبح نظام دفتر الدكان أبسط أداة عربية موثوقة لإدارة النشاط
اليومي للدكان من الهاتف، مع تجربة قريبة من الدفتر الورقي وبنية داخلية
تحافظ على صحة البيانات المالية والمخزنية.

التموضع: المنتج ليس ERP كاملًا، وليس مجرد دفتر ديون. هو نظام تشغيل يومي
خفيف يجمع البيع والدين والمخزون والموردين والأموال في تجربة واحدة.

# **7. الافتراضات والقيود**

- مستخدم واحد ومالك واحد للدكان في النسخة الأولى.

- جهاز موبايل رئيسي واحد لكل دكان في MVP.

- العملة الوحيدة هي الشيكل، ولا توجد ضرائب.

- الإنترنت قد يكون متقطعًا، لذلك لا يجوز ربط البيع الفوري بالخادم.

- كل عملية مالية أو مخزنية معتمدة يجب ألا تُحذف حذفًا صامتًا.

- التطبيق لا يتصل مباشرة بـPostgreSQL؛ الاتصال دائمًا عبر Backend API.

- النسخة المركزية تستطيع استعادة البيانات حتى آخر مزامنة أو نسخة
  احتياطية ناجحة فقط.

# **9. مبادئ تجربة الاستخدام**

- تظهر الكلمات التجارية اليومية بدل المصطلحات المحاسبية.

- المسار الشائع يكون الأقصر، والخيارات المتقدمة تظهر عند الحاجة.

- كل زر حفظ يمنع النقر المتكرر ويعرض حالة نجاح أو فشل واضحة.

- يمكن فتح الفاتورة أو الدفعة من أي حركة مرتبطة.

- لا يطلب التطبيق بيانات غير ضرورية لإتمام العملية.

- تظهر حالة المزامنة بوضوح دون إزعاج المستخدم.

- المستخدم يستطيع القراءة والتصدير والنسخ بعد انتهاء الاشتراك، لكن لا
  يستطيع إنشاء عمليات جديدة.

# **10. رحلة المستخدم الرئيسية**

## **10.1 التهيئة الأولى**

1.  تسجيل الدخول والتحقق من الاشتراك والجهاز.

2.  إدخال اسم الدكان ورقم الهاتف والبيانات الأساسية.

3.  إنشاء حساب الكاش الافتراضي.

4.  إضافة حسابات التحويل حسب أسماء المستخدم.

5.  إضافة المنتجات والوحدات والأرصدة الافتتاحية.

6.  إضافة العملاء والموردين الحاليين وأرصدة البداية عند الحاجة.

7.  إجراء نسخة احتياطية أولى بعد اكتمال التهيئة.

## **10.2 يوم عمل اعتيادي**

8.  يفتح المستخدم لوحة التحكم ويرى المبيعات والتحصيل والديون والمخزون
    والتنبيهات.

9.  يسجل عملية بيع نقدية أو تحويل أو دين أو دفع مختلط.

10. يخصم النظام المخزون ويُنشئ الحركات المالية في عملية ذرية.

11. يسجل المستخدم دفعة عميل أو دفع مورد أو مصروف.

12. تُحفظ العمليات محليًا فورًا وتضاف للمزامنة.

13. عند توفر الإنترنت تُرفع العمليات ويظهر تأكيد المزامنة.

14. في نهاية اليوم يظهر ملخص المبيعات والتحصيل والديون والمصاريف
    والسيولة.

# **12. قواعد العمل المحاسبية**

- دين العميل أصل مستحق، وليس خسارة، ولا يخصم من الربح.

- تحصيل دين قديم يزيد السيولة ولا ينشئ مبيعات جديدة.

- فاتورة المورد تزيد التزام المورد فقط ولا تزيد المخزون تلقائيًا؛ إضافة المخزون تتم عبر عملية مخزون يدوية مستقلة، وتظهر تكلفة البضاعة في الربح عند البيع.

- دفع المورد يخفض المال والالتزام ولا يعد مصروفًا جديدًا.

- سحب المالك لا يعد مصروفًا تشغيليًا.

- نقل الأموال بين الحسابات لا يغير إجمالي الأموال ولا الربح.

- الرصيد الدائن للعميل التزام على الدكان.

- الحركات هي مصدر الحقيقة، والأرصدة المختصرة قابلة لإعادة الحساب.

- لا يجوز حذف أي عملية مالية أو مخزنية معتمدة؛ تستخدم الحركات العكسية
  والتصحيحات.

- كل عملية مركبة تنفذ داخل Transaction واحدة محليًا ومركزيًا.

# **13. متطلبات العمل دون إنترنت والمزامنة**

يجب أن تعمل جميع الوظائف التشغيلية الأساسية داخل الهاتف من خلال SQLite.
PostgreSQL هي النسخة المركزية لإدارة SaaS والاستعادة والبيانات المرفوعة.
لا توجد مزامنة تلقائية بين SQLite وPostgreSQL؛ بل ينفذ النظام بروتوكول
مزامنة مخصصًا.

| **المتطلب**   | **التفصيل**                                                                                     |
|---------------|-------------------------------------------------------------------------------------------------|
| المعرفات      | ينشئ الهاتف UUID لكل كيان وoperationId لكل عملية قبل الاتصال بالخادم.                           |
| Outbox        | تُحفظ العملية وسجل المزامنة في Transaction محلية واحدة.                                          |
| Idempotency   | يمنع الخادم تكرار العملية بقيد فريد على storeId + operationId.                                  |
| Push          | يرفع الهاتف العمليات المعلقة عند توفر الإنترنت.                                                 |
| Pull          | ينزل الهاتف التغييرات باستخدام sync cursor.                                                     |
| Bootstrap     | يعيد الهاتف الجديد بناء SQLite من بيانات PostgreSQL أو أحدث نسخة احتياطية ثم التغييرات اللاحقة. |
| التعارض       | في MVP يوجد جهاز رئيسي واحد؛ التعارضات المتقدمة مؤجلة.                                          |
| حالة المستخدم | يعرض التطبيق آخر مزامنة وعدد العمليات المعلقة وأي خطأ.                                          |
| حد الاستعادة  | البيانات غير المرفوعة قبل فقد الهاتف لا يمكن استعادتها من الخادم.                               |

- وجود Migration قابلة للتطبيق والتراجع وفق سياسة المشروع.

- وجود Validation وصلاحيات وعزل storeId.

- استخدام Transaction عند وجود أكثر من أثر مترابط.

- اختبارات Unit وIntegration وحالات فشل.

- عدم كسر اختبارات الميزات السابقة.

- تحديث OpenAPI والتوثيق وقاموس البيانات.

- مراجعة Kimi، ومراجعة Fable للميزة الخطرة.

- وجود سجل واضح للملفات المعدلة والقرارات المتخذة.

# **24. القرارات النهائية المعتمدة**

- تطبيق صاحب الدكان موبايل كامل، وليس تطبيق ويب كامل.

- لوحة الويب مخصصة لإدارة SaaS والاشتراكات والأجهزة.

- العمل Offline شرط أساسي وليس ميزة اختيارية.

- SQLite هي قاعدة التشغيل المحلية داخل الهاتف.

- PostgreSQL هي قاعدة البيانات المركزية والاستعادة والاشتراكات.

- NestJS + Drizzle ORM هي بنية الـBackend المعتمدة.

- Flutter + Drift هي بنية الموبايل المحلية المعتمدة.

- النسخة الأولى تستخدم جهازًا رئيسيًا واحدًا للدكان.

- الشيكل هو العملة الوحيدة ولا توجد ضرائب في MVP.

- لا حذف صامت للمعاملات المعتمدة.

- المزامنة والنسخ والاستعادة مكونات أساسية في المنتج.

- بساطة الواجهة لا تعني تبسيط القواعد المالية الداخلية.
